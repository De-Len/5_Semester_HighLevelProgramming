# Отчет по чистой архитектуре

## 1. Выделение слоев приложения

В текущем проекте можно выделить следующие неявные слои:

*   **Слой представления/Входной слой (Presentation/Entry Layer):** Отвечает за взаимодействие с пользователем и парсинг входных данных. В данном случае это `Main.kt`, который использует `kotlinx.cli` для обработки аргументов командной строки и вызывает основной сервис.
    *   **Классы/Компоненты:** `Main.kt`

*   **Слой бизнес-логики/Приложения (Application/Business Logic Layer):** Содержит основную логику приложения, координирует работу других сервисов. Здесь происходит аутентификация, авторизация и проверка доступа.
    *   **Классы/Компоненты:** `ResourceAuthorizer`, `AuthenticationService`, `AuthorizationService`, `ResourceParser`, `HashingService`.

*   **Слой данных/Инфраструктуры (Data/Infrastructure Layer):** Отвечает за хранение и доступ к данным. В текущей реализации это имитация базы данных в памяти.
    *   **Классы/Компоненты:** `MockDatabase`, `DataClasses` (User, Resource, Permission).

*   **Слой доменных сущностей (Domain Entities Layer):** Содержит основные бизнес-сущности и правила. В данном проекте это простые структуры данных и перечисления.
    *   **Классы/Компоненты:** `enums` (ExitCode, Role), `exceptions` (InvalidLoginException, etc.), `DataClasses` (User, Resource, Permission).

## 2. Реструктуризация проекта под принципы чистой архитектуры

Для приведения проекта к принципам чистой архитектуры (Clean Architecture) предлагается следующая структура слоев и план реструктуризации:

### Предлагаемые слои Clean Architecture

1.  **Entities (Сущности):** Содержат основные бизнес-правила и данные. Это ядро приложения, которое не должно зависеть от других слоев.
    *   **Содержимое:** `User`, `Resource`, `Permission`, `Role`, `ExitCode`, `Exceptions`.
    *   **Зависимости:** Нет.

2.  **Use Cases (Варианты использования/Интеракторы):** Содержат специфические для приложения бизнес-правила. Они оркестрируют поток данных к сущностям и от них. Они зависят только от слоя Entities.
    *   **Содержимое:** `ResourceAuthorizer` (переименованный в `AuthorizeResourceUseCase` или аналогичный), который будет использовать интерфейсы репозиториев и сервисов.
    *   **Зависимости:** Entities.

3.  **Interface Adapters (Адаптеры интерфейсов):** Преобразуют данные из формата, наиболее удобного для Use Cases и Entities, в формат, наиболее удобный для внешних агентов (UI, базы данных, внешние API). Этот слой включает в себя контроллеры, презентеры, шлюзы (gateways) для баз данных.
    *   **Содержимое:** Интерфейсы репозиториев (`UserRepository`, `ResourceRepository`, `PermissionRepository`), интерфейсы сервисов (`AuthenticationService`, `AuthorizationService`), `ResourceParser`.
    *   **Зависимости:** Entities, Use Cases.

4.  **Frameworks & Drivers (Фреймворки и драйверы):** Самый внешний слой, содержащий конкретные реализации для баз данных, веб-фреймворков, UI и т.д. Этот слой зависит от всех внутренних слоев.
    *   **Содержимое:** `Main.kt` (как точка входа), `MockDatabase` (как конкретная реализация репозиториев), `HashingService` (как утилитарный сервис, который может быть частью инфраструктуры).
    *   **Зависимости:** Entities, Use Cases, Interface Adapters.

### План реструктуризации

1.  **Вынести в отдельные пакеты:**
    *   Создать пакет `domain` для слоя Entities. В него переместить `DataClasses.kt`, `enums` и `exceptions`.
    *   Создать пакет `usecase` для слоя Use Cases. В него переместить `ResourceAuthorizer` (переименовав его).
    *   Создать пакет `application.port` для интерфейсов репозиториев и сервисов (Interface Adapters). Например, `domain.port.in` и `domain.port.out`.
    *   Создать пакет `infrastructure` для конкретных реализаций репозиториев (`MockDatabase`) и утилитарных сервисов (`HashingService`).

2.  **Необходимые интерфейсы/абстракции:**
    *   **`UserRepository`:** Интерфейс для работы с пользователями (например, `findByLogin`).
    *   **`ResourceRepository`:** Интерфейс для работы с ресурсами (например, `findByPath`).
    *   **`PermissionRepository`:** Интерфейс для работы с разрешениями (например, `hasAccess`).
    *   **`AuthenticationService`:** Интерфейс для сервиса аутентификации.
    *   **`AuthorizationService`:** Интерфейс для сервиса авторизации.
    *   **`ResourceParser`:** Интерфейс для парсинга путей ресурсов.

3.  **Изменение зависимостей:**
    *   `AuthorizeResourceUseCase` (бывший `ResourceAuthorizer`) должен зависеть только от интерфейсов `AuthenticationService`, `AuthorizationService`, `ResourceRepository`.
    *   `AuthenticationService` (реализация) будет зависеть от `UserRepository` и `HashingService`.
    *   `AuthorizationService` (реализация) будет зависеть от `PermissionRepository` и `ResourceParser`.
    *   `Main.kt` будет отвечать за сборку всех зависимостей (Dependency Injection) и запуск `AuthorizeResourceUseCase`.

4.  **Пример новой структуры пакетов (Kotlin):**

    ```
    src/main/kotlin
    ├── main.kt
    ├── domain
    │   ├── model
    │   │   ├── User.kt
    │   │   ├── Resource.kt
    │   │   └── Permission.kt
    │   ├── enums
    │   │   ├── ExitCode.kt
    │   │   └── Role.kt
    │   └── exceptions
    │       └── AppExceptions.kt
    ├── usecase
    │   └── AuthorizeResourceUseCase.kt
    ├── application
    │   └── port
    │       ├── in
    │       │   └── AuthorizeResourceCommand.kt (DTO for use case input)
    │       ├── out
    │       │   ├── UserRepository.kt
    │       │   ├── ResourceRepository.kt
    │       │   └── PermissionRepository.kt
    │       └── shared
    │           ├── AuthenticationService.kt
    │           ├── AuthorizationService.kt
    │           └── ResourceParser.kt
    └── infrastructure
        ├── persistence
        │   └── mock
        │       ├── MockDatabase.kt
        │       ├── MockUserRepositoryAdapter.kt
        │       ├── MockResourceRepositoryAdapter.kt
        │       └── MockPermissionRepositoryAdapter.kt
        ├── service
        │   ├── HashingServiceAdapter.kt
        │   └── ResourceParserAdapter.kt
        └── cli
            └── CliArgumentParser.kt (if `Main.kt` logic is extracted)
    ```

Этот план позволит значительно улучшить модульность, тестируемость и поддерживаемость проекта, следуя принципам чистой архитектуры.
